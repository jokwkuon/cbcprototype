# Proposed operational migration contracts — approval required

REQ-003/004/007/008/009/010/011 and proposed REQ-015. The [review-only SQL skeleton](proposals/operational-workflows.sql) supplies proposed relational DDL with a rollback wrapper and no browser grants. It was not executed or SQL-verified; incomplete business constraints and policies are marked explicitly. Neither it nor the contracts below is an applied migration. Do not place policy-dependent drafts in `database/migrations` or the executable SQL test proposal glob. Generate reviewed migration files only after the relevant business/access decisions are accepted.

| Proposed migration | Relational components and invariants | Backfill / rollback / acceptance |
|---|---|---|
| Independent mentorship affiliation | Replace the pair's two organization/contact composite FKs with independent mentor/mentee contact FKs; retain non-self constraint, program/cohort composite FK and explicit administering organization if approved | First validate every existing contact ID; no inferred affiliation changes. Rollback to old FKs fails if cross-org pairs exist, requiring explicit reconciliation. MENT-01/02 and reparent tests |
| Program access and sensitive partition | `program_staff_assignments(program_id,profile_id,capability,revoked_at)`; unique active assignment; application identity, restricted details, review notes and safeguarding data split into distinct tables. Fixed approved capability vocabulary; trusted operator manages grants | No automatic broad-role → sensitive capability backfill. RLS checks active profile + assignment on each table. Invoker projections only; revoke default function execution. STUD-01 negative tests for every channel |
| Applications and review | `applications(id,program_id,cohort_id,recipient_id,submitted_at,recorded_status,version)`; cohort/program composite FK; `application_reviews(id,application_id,reviewer_id,decision,reviewed_at,conflict_state)`; explicit approved status transitions in atomic invoker command | Existing enrollments stay intact; no applications fabricated from participants. Unique application scope and rubric/version need CBC decision. Optimistic concurrency and transaction rollback tests |
| Recorded awards | `program_awards(id,application_id,enrollment_id,amount,currency,awarded_on,decision_reference)` with exact numeric and explicit approved sign/currency constraints | Existing enrollment support remains declared support; never auto-backfill paid awards. Disbursements/refunds require separate approved ledger and writer matrix. AWARD-01/FIN-01 |
| Membership responsibility | Optional responsible profile FK only if CBC chooses independent responsibility; otherwise reuse organization owner as a displayed inherited value | Never infer historical staff or reassign organization. | Internal sessions/attendance | `program_sessions(id,program_id,starts_at,ends_at,location,recorded_status)`; `session_attendance(id,session_id,recipient_id,recorded_state,recorded_by,version)` unique session/recipient; approved correction events | Typed Giving Event references stay financial references; explicit unique bridge if approved. No public sync. EVENT-01; timezone/duplicate/correction/access tests |
| Import staging/duplicate review | `import_batches(id,source_label,checksum,status,actor_id,idempotency_key)`; `import_rows(batch_id,row_number,validation_state,proposed_reference)` unique batch/row; `duplicate_reviews` explicit candidates/resolution | Staging tables private, minimal retention, no arbitrary SQL mappings; references to approved target records only. No automatic name-based merge. IMPORT-01 and dry-run/no-write tests |
| Actor audit | Protected append-only event table with actor from authenticated context, server time, operation and approved minimal before/after fields; indexes on subject/time and actor/time | Define deletion/retention before implementation; grant neither browser insert nor update/delete. Carefully scoped trigger function with fixed search path and explicit EXECUTE revocation if definer needed. AUDIT-01 |

For each approved migration: document forward SQL, existing-data validation, lock/transaction implications, RLS/grants/functions/index review, local synthetic replay, denied-role API tests, reconciliation counts, backup/restore and forward-fix strategy. Approval of a design is not approval to modify hosted Supabase.

The **applied local performance migration** `20261104214044_operational_directory.sql` is separate: it adds two SELECT-only security-invoker views, no base-table policy, lifecycle or accounting changes. Dropping those views would break the new directories, so rollback must restore the prior application alongside dropping views. Existing organization ID/name filter options remain a known remaining scale limit.
